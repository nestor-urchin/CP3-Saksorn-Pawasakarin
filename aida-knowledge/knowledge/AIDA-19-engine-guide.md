# AIDA-19 · คู่มือเรียก engine (Intake Review, วิเคราะห์, โหมดสำรวจ)
> ไฟล์: AIDA-19 | เวอร์ชัน: 3.0 | ส่วนหนึ่งของ AIDA Knowledge Pack | engine: `aida_engine.py` v3.0.0 · Registry 1.2
> ไฟล์นี้ตอบคำถาม: เรียก engine ตามลำดับใด, brief และคำตอบยืนยัน (answers) มีรูปแบบอย่างไร, Intake Review ข้อ A–E คืออะไร, คำตอบแบบใดถือว่ายืนยัน, โหมดสำรวจและการเลื่อนเป็น Finding ทำอย่างไร, mapping profile ใช้อย่างไร, Finding ของข้อมูล C/A รวมกันอย่างไร, ข้อความผิดพลาดหมายความว่าอะไร

## สรุปสั้น
AIDA วิเคราะห์ข้อมูลด้วย engine ไฟล์เดียว `aida_engine.py` v3.0.0 ที่ทดสอบแล้ว (โหลดตาม AIDA-16) โดยเรียกเพียง **`inspect` → (ผู้ตรวจสอบยืนยันครั้งเดียว) → `confirm` + `run`**
- ตัวเลขทุกตัวที่แสดงต้องมาจากผลของ engine — AIDA ไม่คำนวณเอง และไม่เขียนโค้ดวิเคราะห์แทนการ์ดรับรอง
- จุดยืนยันมีจุดเดียวคือ **Intake Review** (แทนจุดยืนยัน 1 และ 2 ของ B1)
- คำถามที่ไม่มีการ์ดรับรอง → **โหมดสำรวจ** (ข้อ 5) ซึ่งผลมีป้ายและเลื่อนเป็น Finding ได้เมื่อผู้ตรวจสอบสั่งเท่านั้น
- ข้อผิดพลาดทุกข้อเป็นข้อความภาษาไทยที่บอกวิธีแก้ (`AidaError`) ไม่ใช่ traceback

## 1. ลำดับการเรียก
| ขั้น | เรียก | ได้ |
|---|---|---|
| 0 | โหลด engine ตาม AIDA-16 | `aida` (ตรวจ `aida.__version__ == "3.0.0"`) |
| 1 | `r = aida.inspect(files, brief)` (หรือ `mapping=` ข้อ 6) | `r["intake"]` (ร่าง), `r["review_th"]` (ข้อความ Intake Review), `r["changes"]` |
| 2 | แสดง `r["review_th"]` **ทั้งข้อความตามตัวอักษร** แล้วรอผู้ตรวจสอบ | — |
| 3 | `it = aida.confirm(r["intake"], answers, "intake.json")` | intake ที่ยืนยัน + ไฟล์ `intake.json` (มี `it["intake_path"]`) |
| 4 | `res = aida.run(files, it, out_dir)` ในคำตอบเดียวกับข้อ 3 | `res["summary_th"]`, `res["findings"]`, `res["paths"]` (workbook, dashboard, csv_dir), `res["warnings"]` |
| 5 | แสดง `summary_th`, คำเตือน และลิงก์ไฟล์ output | — |

- `files` = dict `{ชื่อตาราง: ที่อยู่ไฟล์}` เช่น `{"payments": "/mnt/data/payments.csv", "contracts": "/mnt/data/contracts.csv"}` (หรือ list ของที่อยู่ไฟล์; CSV UTF-8 / TIS-620 หรือ XLSX ทุก sheet)
- `run()`, `data()` และ `trace()` ทำงานจาก `intake.json` + ไฟล์เท่านั้น ถ้าตัวแปรใน Code Interpreter หาย → โหลด engine ใหม่ (AIDA-16) แล้วส่งที่อยู่ `intake.json` แทน dict โดยไม่ถามยืนยันซ้ำ
- ไฟล์เกิน 80,000 รายการ → แนะนำให้แบ่งไฟล์ตามเดือน (ขนาดที่ทดสอบแล้ว)

### รูปแบบ brief (AIDA แยกจากข้อความอิสระของผู้ตรวจสอบ)
```text
brief = {
  "context": "บริบทงาน 1-2 บรรทัด (ประเภทข้อมูล ช่วงเวลา ตารางที่เชื่อมกัน)",
  "columns": {"ชื่อคอลัมน์ตามไฟล์": "ความหมายตามที่ผู้ตรวจสอบเขียน (คัดลอกถ้อยคำเดิม)"},
  "conditions": ["เงื่อนไขทีละข้อ ตามถ้อยคำเดิม"],
  "concerns": ["Risk Concern ทีละข้อ ตามถ้อยคำเดิม"],
  "materiality": {"type": "ก" | "ข" | "ไม่ระบุ", "amount": ตัวเลข, "basis": "ข้อความ"}
}
```
- ใส่เฉพาะสิ่งที่ผู้ตรวจสอบเขียน ห้ามเติมความหมายคอลัมน์ที่ไม่ได้บอก (engine เดาและติด ❓ ให้เอง)
- คอลัมน์ที่ผู้ตรวจสอบบอกว่า "ไม่แน่ใจ" → ไม่ใส่ใน columns

## 2. Intake Review (ข้อความ `review_th`)
| ข้อ | เนื้อหา | ผู้ตรวจสอบทำอะไร |
|---|---|---|
| A. ความหมายคอลัมน์ | ✅ ตรงกับคำอธิบาย / ⚠️ ขัดกับข้อมูล / ❓ เดาให้ช่วยยืนยัน / ⚪ ไม่ทราบ พร้อมความมั่นใจ เหตุผล ตัวอย่างค่า ค่ารหัส และ % การเชื่อมตาราง | ยืนยัน หรือแก้บทบาท ⚠️ ❓ ⚪ |
| B. ความพอเพียงตาม Risk Concern | Concern → ความเสี่ยงใน Risk Library (AIDA-18): ✅ พร้อม / 🟡 บางส่วน / ❌ ไม่พอ + เหตุผล + Data Request; Concern ที่ไม่ตรงคลัง → แจ้งว่าจะใช้โหมดสำรวจ | รับทราบ / ขอข้อมูลเพิ่ม |
| C. เงื่อนไขที่เข้าใจ | ตัวกรองที่แปลงได้ (❓ พร้อมจำนวนแถวที่ตัด) และเงื่อนไขที่ยังแปลงไม่ได้ + ค่าเกณฑ์ขององค์กร | ยืนยันตัวกรอง / ระบุค่าองค์กร |
| D. ความเสี่ยงที่แนะนำเพิ่ม | ความเสี่ยงในคลังที่ข้อมูลรองรับแต่ยังไม่ได้ขอ + ตัวเลขเบื้องต้นจาก engine | เลือกเพิ่ม (ไม่ตอบ = ไม่เพิ่ม) |
| E. วันที่ / คุณภาพข้อมูล / Materiality / แผน Run-Skip | รูปแบบวันที่ที่แปลง (รวม พ.ศ.), แถวที่แปลงไม่ได้, ผลตรวจ record_id, Materiality, การ์ดที่ Run / Skip พร้อมเหตุผล | ระบุ Materiality ก./ข./ไม่ระบุ |

ปิดท้ายด้วย "ยืนยันทั้งหมด หรือแก้เฉพาะข้อ ⚠️ ❓ D แล้วเริ่มวิเคราะห์" — ถ้า `profile_status` ขึ้นต้นด้วย STOP (เช่น ไม่มี record_id หรือซ้ำ) ให้แจ้งเหตุผลและสิ่งที่ต้องแก้ แล้วหยุด (AIDA-02)

## 3. กติกาการยืนยัน
- คำยอมรับ เช่น "ยืนยัน", "ตกลง", "ok", "ไปต่อ" **หรือการแก้ค่าใด ๆ** = ยืนยันแล้ว → เรียก `confirm` แล้ว `run` **ทันทีในคำตอบนั้น** ไม่ถามซ้ำ
- ไม่ระบุ Materiality → `{"type": "ไม่ระบุ"}` (Materiality = "ไม่ได้ประเมิน", Priority = Confidence) และแจ้งในคำตอบ
- ไม่ตอบข้อ D → ไม่เพิ่มความเสี่ยง (`add_risks` ว่าง) — ห้ามเพิ่มเอง
- ผู้ใช้ขอให้ข้ามการยืนยันทั้งหมด → แสดง Intake Review ก่อนเสมอ (Human Accountable) แต่คำตอบสั้น ๆ อย่าง "ตกลง" ก็พอให้วิเคราะห์ต่อ

### รูปแบบ answers ของ `confirm`
```text
answers = {
  "roles": {"คอลัมน์": "บทบาท"} หรือ {"ตาราง": {"คอลัมน์": "บทบาท"}},   # เฉพาะที่แก้; "ไม่ใช้" = ไม่นำเข้า; custom:<ชื่อ>; list = บทบาทรับรอง 1 + custom
  "filters": [{"column": "คอลัมน์", "op": "== != in not in > >= < <= between", "value": ค่า}],
  "org_values": {"KEY ตาม AIDA-14": ค่า},       # ค่าขององค์กร ใช้เฉพาะ run นี้ ติดป้าย "ค่าขององค์กร"
  "add_risks": ["รหัสความเสี่ยงจากข้อ D ที่ผู้ตรวจสอบเลือก"],
  "materiality": {"type": "ก" | "ข" | "ไม่ระบุ", "amount": ฐานเป็นตัวเลข, "basis": "คำอธิบาย"},
  "reviewer": "ชื่อผู้ตรวจสอบที่ยืนยัน",
  "columns": {"คอลัมน์": "ความหมายที่ผู้ตรวจสอบเพิ่ม"},
  "code_values": {"ตาราง.คอลัมน์": {"รหัส": "ความหมาย"}}
}
```
- ใส่เฉพาะ key ที่มีคำตอบ; key อื่นที่ไม่รู้จักถูกปฏิเสธเป็นภาษาไทย
- **`filters` แทนที่ตัวกรองทั้งชุด** — ถ้าส่ง ให้ใส่ตัวกรองที่ engine เสนอไว้ในข้อ C (เช่น `status != C`) รวมกับตัวกรองใหม่ด้วย
- เงื่อนไขที่ไม่ใช่ "คอลัมน์ = ค่า" (ช่วงวันที่, มากกว่า/น้อยกว่า, หลายค่า) engine แปลงไม่ได้และแสดงเป็น ❓ ในข้อ C → AIDA ส่งเป็นตัวกรองเอง เช่น "ดูเฉพาะ 1 ม.ค. – 31 ส.ค. 2026" → `{"column": "pay_date", "op": "between", "value": ["2026-01-01", "2026-08-31"]}`; "ยอดตั้งแต่ 1,000" → `{"column": "amount", "op": ">=", "value": 1000}` (คอลัมน์ต้องเป็นชื่อตามไฟล์)
- ค่า materiality "ข." ให้ใส่ฐานที่คำนวณแล้วโดยผู้ตรวจสอบเป็น `amount` — AIDA ไม่คำนวณฐานเอง

## 4. การอ่านผลและการรวม Finding ของข้อมูล C / A
- `entity_type` ใช้ชื่อตามประเภทข้อมูล: A → vendor / document / user, C → borrower / payer / contract
- **จ่ายซ้ำ (DUP-PAY)**: ถ้ารายการซ้ำทุกรายการมีเลขเอกสาร (`document_no`) เดียวกัน Finding ใช้เลขเอกสารเป็น entity (`entity_type = document`) เช่น ใบแจ้งหนี้ INV-7781; ข้อมูลสินเชื่อที่ไม่มีเลขเอกสารรายงานตามสัญญา (C-R3)
- **ยอดซ้ำ / ยอดกลม (FOR-REPEAT / FOR-ROUND)** ถูกรวมเข้า Finding A-R2 ของการแบ่งรายการ (SPLIT-LIMIT) **เฉพาะเมื่อรายการของมันเป็นส่วนหนึ่งของรายการ SPLIT-LIMIT** (entity และงวดเดียวกัน) — ยอดซ้ำบนรายการอื่นของผู้ขายเดียวกันยังเป็น Finding G-R4 แยก
- Finding ทุกรายการเป็น "รอ Human Review" และเป็นสัญญาณให้ตรวจสอบเพิ่มเติม ไม่ใช่ข้อสรุป
- ไล่เส้นทางเงินเพิ่ม (ข้อมูล E): `aida.trace(files, "intake.json", "บัญชี", direction="both", period=None, out_dir=...)` → `summary_th` + CSV (FLOW-TRACE ไม่ใช่การ์ดรับรอง ไม่สร้าง Finding)

## 5. โหมดสำรวจ (คำถามนอกการ์ดรับรอง)
1. แจ้ง: "ไม่มีการ์ดรับรองสำหรับคำถามนี้ — วิเคราะห์ในโหมดสำรวจ"
2. `d = aida.data("intake.json")` → `d["transactions"]` (และ `d["accounts"]` ถ้ามี) ที่แปลงบทบาทและใช้ตัวกรองแล้ว รวม custom; ชื่อคอลัมน์เดิมอยู่ใน `df.attrs["original_names"]`
3. เขียนโค้ด pandas สั้น ๆ ที่ตอบคำถามนั้น — ห้ามแก้ engine และห้ามใช้แทนการ์ดรับรองที่มีอยู่
4. `eid = aida.explore_log(question, code, result, note, intake="intake.json")` → บันทึกคำถาม โค้ดเต็ม ผล และเวลา ลง `explore_log.json` ข้าง `intake.json` (ตาม `intake["intake_path"]`) และ sheet Exploratory
5. แสดงผลพร้อมป้าย **"โหมดสำรวจ — ยังไม่ผ่านการรับรอง"** + ข้อจำกัด + `eid`; ตัวเลขเกณฑ์ที่ใช้ต้องอ้าง key ใน AIDA-14 หรือระบุว่า "ผู้ใช้กำหนด"
6. เลื่อนเป็น Finding **เฉพาะเมื่อผู้ตรวจสอบสั่งชัดเจนและระบุชื่อผู้ทบทวน**: `aida.promote(eid, entity, risk, period, reason, reviewer, intake="intake.json")`
   - `risk` = รหัสใน Risk Library (AIDA-18) หรือ `RX` (ความเสี่ยงจากโหมดสำรวจ)
   - Confidence สูงสุด "กลาง" (ค่าที่สูงกว่าถูกลดให้), `reviewer` บังคับ, `source = "exploratory"`, ป้าย "จากโหมดสำรวจ" ถาวร
   - `run()` ครั้งถัดไปรวม Finding ที่เลื่อนแล้วเข้า Findings, Exploratory sheet และ Dashboard
- ไม่มีชื่อผู้ทบทวน → ถามชื่อก่อน ห้ามเลื่อนเอง; เหตุผลที่เลื่อนใช้ถ้อยคำไม่กล่าวหา

## 6. Mapping profile (ใช้ซ้ำรอบถัดไป)
- ผู้ตรวจสอบขอบันทึก → `aida.save_mapping(it, "ชื่อ")` → `mapping-ชื่อ.json` (บทบาท, ความหมายคอลัมน์, ค่ารหัส, ตัวกรอง, ค่าองค์กร, ผู้ยืนยัน, วันที่) ให้ผู้ใช้เก็บใน SharePoint ของทีม
- รอบถัดไป: `aida.inspect(files, brief, mapping="mapping-ชื่อ.json")` ใช้ค่าเดิม และ Intake Review ถามเฉพาะสิ่งที่เปลี่ยน (`r["changes"]`: คอลัมน์ใหม่ / หาย / รูปแบบเปลี่ยน) — ยังต้องยืนยันครั้งเดียวตามข้อ 3

## 7. การแก้ปัญหา (ข้อความภาษาไทยจาก engine)
| ข้อความขึ้นต้นด้วย | ความหมาย | ทำอย่างไร |
|---|---|---|
| ไม่พบไฟล์ ... | ที่อยู่ไฟล์ข้อมูล / intake / mapping ไม่ถูก | ตรวจที่อยู่ หรือขอให้ผู้ใช้แนบไฟล์ใหม่ครั้งเดียว |
| ไม่พบไฟล์ AIDA-14-configuration-registry.md | engine หาค่าเกณฑ์ไม่เจอ | วาง AIDA-14 ข้าง engine ตาม AIDA-16 |
| ไม่รู้จักคำตอบ ... / ไม่รู้จักค่าเกณฑ์ ... | answers มี key หรือชื่อ KEY ที่ไม่มี | ใช้ key ตามข้อ 3 และชื่อ KEY ตาม AIDA-14 |
| ไม่รู้จักรหัสความเสี่ยง ... | add_risks / risk ไม่อยู่ใน Risk Library | เลือกจาก AIDA-18 หรือใช้โหมดสำรวจ (RX) |
| ตัวกรองข้อ n ... | ตัวกรองผิดรูปแบบ / ไม่พบคอลัมน์ / ค่าเทียบไม่ได้ | แก้ตามข้อความ (เช่น between ต้องมี 2 ค่า) |
| Materiality แบบ ก. ต้องมี amount | เลือก ก./ข. แต่ไม่มีฐาน | ถามฐาน หรือใช้ "ไม่ระบุ" |
| ไฟล์ของตาราง ... เปลี่ยนไปจากตอนยืนยัน Intake (คำเตือน) | sha256 ไม่ตรงกับตอนยืนยัน | แจ้งผู้ใช้ว่าผลอาจต่างจาก Intake Review |
| ต้องระบุผู้ตรวจสอบ (reviewer) | promote โดยไม่มีชื่อผู้ทบทวน | ถามชื่อผู้ทบทวนก่อนเลื่อน |
| ไม่พบ EXP-n ในบันทึกโหมดสำรวจ | promote ก่อน explore_log หรือคนละ intake | เรียก explore_log ก่อน และส่ง intake= ชุดเดียวกัน |
| Money Flow ต้องมีบทบาท entity และ counterparty | trace กับข้อมูลที่ไม่ใช่การโอนเงิน | ใช้ได้กับข้อมูล E เท่านั้น |
| เกิดข้อผิดพลาดภายใน engine | กรณีที่ไม่คาดไว้ | แจ้งข้อความเต็มแก่ผู้ใช้ และส่งให้ผู้ดูแล AIDA — ห้ามเขียนโค้ดแทน |

## ข้อห้าม (Guardrails)
- ห้ามคำนวณหรือแต่งตัวเลขเอง — ทุกตัวเลขมาจาก engine (`review_th`, `summary_th`, ตาราง findings)
- ห้ามเรียก `run` ก่อนผู้ตรวจสอบยืนยัน Intake Review และห้ามถามยืนยันซ้ำเมื่อผู้ตรวจสอบยืนยันแล้ว
- ห้ามเพิ่มความเสี่ยงจากข้อ D เอง ห้ามเลื่อนผลโหมดสำรวจเป็น Finding เองหรือโดยไม่มีชื่อผู้ทบทวน
- ห้ามแก้ engine และห้ามใช้โหมดสำรวจแทนการ์ดรับรองที่มีอยู่
- ห้ามใช้ถ้อยคำกล่าวหา และห้ามใช้คำว่า "บัญชีม้า" — ใช้ "สอดคล้องกับ … pattern ควรตรวจสอบเพิ่มเติม" (AIDA-11)
