# AIDA Phase C1 — Generic Engine, Risk-Driven Intake & Exploratory Mode — Design Spec

- วันที่: 2026-11-06
- สถานะ: รอผู้ใช้ตรวจ (Draft for review)
- ต่อยอดจาก: ระยะ A (`2026-11-03-aida-knowledge-pack-design.md`) และ B1 (`2026-11-03-aida-phase-b1-design.md`, Knowledge Pack v2.0.1)

## 1. เป้าหมาย (Intent)

ปัญหาจากการใช้ข้อมูลจริง: AIDA v2.0 วิเคราะห์ได้เฉพาะ use case ที่มีการ์ดใน Knowledge (Mule Accounts) เพราะการ์ดผูกกับชื่อคอลัมน์ธุรกรรมโอนเงิน และการทดสอบใน Copilot ติดที่จุดยืนยัน

C1 ทำให้ AIDA:
1. **วิเคราะห์ข้อมูลได้หลายประเภท** ด้วยการ์ดกลางที่ทำงานตาม **บทบาทคอลัมน์ (role)** ไม่ใช่ชื่อคอลัมน์
2. **รับคำอธิบายจากผู้ตรวจสอบ** (บริบท ความหมายคอลัมน์ เงื่อนไข Risk Concern) แล้ว **ประเมินความพอเพียงของข้อมูลต่อความเสี่ยง** เดาความหมายคอลัมน์ที่ไม่ได้อธิบาย และ **แนะนำความเสี่ยงเพิ่ม** — ทั้งหมดผ่าน **Intake Review** ที่ผู้ตรวจสอบยืนยันครั้งเดียว
3. **ตอบคำถามนอกการ์ด** ผ่าน **โหมดสำรวจ** ที่ AIDA เขียนโค้ดเองภายใต้การควบคุม และเลื่อนเป็น Finding ได้เมื่อผู้ตรวจสอบทบทวน
4. **รันด้วย Python engine ไฟล์เดียว** (`aida_engine.py`) ที่ทดสอบแล้ว — Copilot เรียกเพียง `inspect` → (ยืนยัน) → `run`

หลักการระยะ A คงไว้ทั้งหมด (ไม่กล่าวหา, ค่ามาตรฐานจาก AIDA-14, แยก C/M/P, Skip/Stop ต้องมีเหตุผล, Human Accountable, Evidence First, Reproducible)

### Roadmap ระยะ C
| ช่วง | ขอบเขต |
|---|---|
| **C1 (spec นี้)** | engine + บทบาท + Intake Review + Risk Library + โหมดสำรวจ; การ์ดรับรองสำหรับข้อมูล **E โอนเงิน**, **C สินเชื่อ/ชำระค่างวด**, **A จ่ายผู้ขาย** |
| C2 | การ์ดรับรอง + preset: บัตรเครดิต, ประกันชีวิต |
| C3 | การ์ดรับรอง + preset: กองทุน/การลงทุน, มูลนิธิ, สหกรณ์ |
ระหว่างรอ C2/C3 ข้อมูลประเภทเหล่านั้นใช้การ์ดกลางที่บทบาทพอ + โหมดสำรวจได้

### ข้อตกลงหลัก
| หัวข้อ | ข้อตกลง |
|---|---|
| ที่มาของโค้ด | **Python engine ไฟล์เดียว** ทดสอบใน repo, มีเวอร์ชัน (ผู้ใช้เลือกใช้ Python engine) |
| การส่ง engine ให้ Copilot | **แนวทาง 3: engine อยู่ใน Knowledge** — ถ้า spike พบว่าทำไม่ได้ → **แนวทาง 2: แนบ/อ่าน engine จาก SharePoint** (engine เหมือนเดิม) |
| บทบาทคอลัมน์ | **14 บทบาทคงที่** (ข้อ 4.1) + ผู้ตรวจสอบเพิ่มเองได้เป็น `custom:<ชื่อ>` |
| จุดยืนยัน | **Intake Review จุดเดียว** แทนจุดยืนยัน 1 และ 2 ของ B1 |
| โหมดสำรวจ | ผลเลื่อนเป็น Finding ได้หลังผู้ตรวจสอบทบทวน; **Confidence สูงสุด "กลาง"**; ป้าย "จากโหมดสำรวจ" ถาวร; ต้องมีชื่อผู้ทบทวน |
| ข้อมูลอ่อนไหว / output | คงตาม B1: แสดงข้อมูลเต็ม + ป้ายเตือน; Workbook + CSV + HTML Dashboard |
| ข้อจำกัด | Knowledge ≤ 20 ไฟล์; Instructions ≤ 8,000 ตัวอักษร |

### เกณฑ์ความสำเร็จ
1. Spike ใน Copilot (ข้อ 7.1) ตัดสินแนวทาง 3 หรือ 2 ได้ชัด
2. ข้อมูลตัวอย่าง E/C/A ได้ Finding ตรงเฉลย; ชุด E ตรงเฉลย B1 เดิม (19 Finding + 1 เครือข่าย)
3. ชื่อคอลัมน์ 3 แบบ (อังกฤษ / ไทย / รหัสย่อ) ได้ Finding เท่ากันเมื่อบทบาทถูก
4. `assess_sufficiency` และ `suggest_risks` ได้ผลตรงเฉลย Intake และ deterministic
5. Tests ผ่านทั้ง pandas 3 และ 1.5.3; validator ผ่าน
6. Eval ใน Copilot (ข้อ 7.4) ผ่าน

## 4. รายละเอียดการออกแบบ

### 4.1 บทบาทคอลัมน์ (14 บทบาท + custom)
| บทบาท | ความหมาย |
|---|---|
| `record_id` | รหัสรายการ (**บังคับ**; ไม่มี/ซ้ำ → STOP) |
| `date` | วันเวลารายการ |
| `amount` | ยอดเงิน |
| `entity` | ผู้ทำรายการหลัก (บัญชีต้นทาง, ผู้กู้, ผู้ขาย) |
| `counterparty` | คู่รายการ (บัญชีปลายทาง, ผู้ชำระแทน) |
| `contract` | สัญญา / กรมธรรม์ / บัตร / ใบแจ้งหนี้ |
| `category` | หมวด |
| `channel` | ช่องทาง / สาขา |
| `created_by` | ผู้บันทึก |
| `approved_by` | ผู้อนุมัติ |
| `document_no` | เลขเอกสาร |
| `limit` | วงเงิน / ค่างวด |
| `due_date` | วันครบกำหนด |
| `opened_at` | วันเปิดบัญชี/สัญญา (ตาราง master) |

- **บทบาทกำหนดเอง** `custom:<ชื่อ>`: ผู้ตรวจสอบเพิ่มได้ไม่จำกัด; การ์ดรับรองไม่ใช้; โหมดสำรวจใช้ได้; ส่งต่อไปใน Evidence/Workbook
- **หลายตาราง**: ตารางรอง (เช่น master บัญชี, ตารางงวด) จับคู่ผ่านคอลัมน์เชื่อมที่ผู้ตรวจสอบยืนยัน
- **Preset** E/C/A + **พจนานุกรมชื่อคอลัมน์** ไทย/อังกฤษ ใช้เสนอบทบาทเท่านั้น — ผู้ตรวจสอบยืนยันเสมอ

### 4.2 การ์ดรับรองใน C1
| การ์ด | บทบาทที่ต้องมี | ใช้กับ | ที่มา |
|---|---|---|---|
| ยอดโดดเด่น (MAD) | amount (+category) | ทุกประเภท | B1 |
| การกระจุกตัว (share/HHI) | amount + entity หรือ counterparty | ทุกประเภท | ใหม่ (ระยะ A 5.2) |
| ช่วงสิ้นงวด | date (+amount) | ทุกประเภท | ใหม่ (ระยะ A 5.4) |
| นอกเวลาทำการ | date + entity | ทุกประเภท | B1 |
| Velocity / Spike | entity + date | ทุกประเภท | B1 |
| **จ่ายซ้ำ** | entity + amount + date (+counterparty, document_no) | A, C | ใหม่ |
| **ใกล้วงเงิน / แบ่งรายการ** | amount + limit (+entity, date) | A, C | ใหม่ (ระยะ A 5.6) |
| **Benford / ยอดกลม / ยอดซ้ำ** | amount (+entity) | ทุกประเภท | ใหม่ (ระยะ A 5.6) |
| **SoD ผู้บันทึก = ผู้อนุมัติ** | created_by + approved_by | A | ใหม่ |
| **ชำระใกล้วันครบกำหนด** | date + due_date + contract | C | ใหม่ |
| **ผู้ชำระคนเดียวหลายสัญญา** | counterparty + contract | C | ใหม่ |
| คู่ค้าใหม่ / Counterparty profile | entity + counterparty + date | E, A, C | B1 |
| Cycle, Funnel, Dwell, New-account, Mule pattern, Mule network, Money Flow, Layering | entity + counterparty + date (+opened_at) | E | B1 |

แต่ละการ์ด: Run/Skip ตามบทบาทที่มี (Skip ต้องบอกบทบาทที่ขาด), เกณฑ์จาก `cfg[KEY]` (AIDA-14), Evidence schema เดิม + `roles_used` และชื่อคอลัมน์ต้นทาง

### 4.3 Intake Review (จุดยืนยันจุดเดียว)
**Input จากผู้ตรวจสอบ** (ข้อความอิสระ): ไฟล์, บริบท, ความหมายคอลัมน์ (บางส่วนก็ได้), เงื่อนไข, Risk Concern

**ขั้นตอน (ข้อ 1–15 ตามที่ตกลง):**
1. AIDA แยกคำอธิบายเป็น: บริบท / คำอธิบายคอลัมน์ / เงื่อนไข / Risk Concern
2. `aida.inspect(files, brief)` ใน engine:
   - อ่านไฟล์, sha256, Data Reference, ตรวจ record_id
   - `profile_columns`: ชนิด, % ว่าง, % ไม่ซ้ำ, ช่วงค่า, top-5, ตัวอย่าง 3 ค่า, รูปแบบ (เลขบัญชี, เลขบัตรประชาชน 13 หลัก, รหัส, วันที่/เวลา, ยอดติดลบ, ข้อความไทย), ความสัมพันธ์ระหว่างคอลัมน์ (เช่น C = A − B, X ≤ Y เสมอ, % ที่ X == Y)
   - แปลงวันที่ (dd/mm, พ.ศ., เดือนไทย) และยอดเงิน — กติกา B1
   - `suggest_roles`: จากคำอธิบายผู้ตรวจสอบ + preset + พจนานุกรม + profile → บทบาท + ความมั่นใจ + เหตุผล; ไม่รู้ → "ไม่ทราบ" (ห้ามเดามั่ว)
   - `check_descriptions`: คำอธิบายที่ขัดกับ profile (เช่น "ยอดสุทธิ" แต่มีค่าติดลบ)
   - `assess_sufficiency(risks)`: จับคู่ Risk Concern กับ Risk Library → การ์ด → ✅ พร้อม / 🟡 บางส่วน / ❌ ไม่พอ + เหตุผล + Data Request
   - `suggest_risks`: ความเสี่ยงใน Risk Library ที่ข้อมูลรองรับแต่ยังไม่ได้ขอ + ตัวเลขเบื้องต้นจาก engine (เช่น "~40 คู่ที่อาจเป็นการชำระซ้ำ")
   - แผน Run/Skip ทุกการ์ด
3. AIDA ตีความผลของ engine (ความหมายคอลัมน์เป็นภาษาไทย) — **ตัวเลขทุกตัวมาจาก engine**
4. แสดง **Intake Review**:
   - **A. ความหมายคอลัมน์**: ✅ ตรงกับคำอธิบาย / ⚠️ ขัดกับข้อมูล / ❓ เดาให้ช่วยยืนยัน / ⚪ ไม่ทราบ (เก็บเป็น custom หรือไม่ใช้)
   - **B. ความพอเพียงตาม Risk Concern** + **Data Request**
   - **C. เงื่อนไขที่เข้าใจ**: ตัวกรอง + ค่าเกณฑ์ขององค์กร (แทนค่ามาตรฐาน AIDA-14 ติดป้าย "ค่าขององค์กร")
   - **D. ความเสี่ยงที่แนะนำเพิ่ม** — ผู้ตรวจสอบเลือก (ไม่เพิ่มเองจนกว่าจะตอบ)
   - **E. วันที่/คุณภาพข้อมูล, Materiality (ก./ข./ไม่ระบุ), แผน Run/Skip**
   - ปิดท้าย: "ยืนยันทั้งหมด หรือแก้เฉพาะข้อ ⚠️ ❓ D แล้วเริ่มวิเคราะห์"
5. **กติกาการยืนยัน**: คำยอมรับ ("ยืนยัน", "ตกลง", "ok", "ไปต่อ") หรือการแก้ค่า = ยืนยัน → เรียก `aida.run(...)` ทันทีในคำตอบนั้น; ไม่ระบุ Materiality = "ไม่ระบุ"; ไม่ตอบข้อ D = ไม่เพิ่มความเสี่ยง
6. **ความทนทาน**: `run()` อ่านไฟล์และสร้างทุกอย่างใหม่จาก intake ที่ยืนยัน (`intake.json`) — ไม่พึ่งตัวแปรจากข้อความก่อน
7. ความเสี่ยงที่ไม่มีใน Risk Library → แจ้งตั้งแต่ Intake ว่าจะใช้โหมดสำรวจ

### 4.4 Risk Library (AIDA-18 + engine)
ความเสี่ยงแต่ละข้อ: `risk_id`, ชื่อไทย, คำอธิบาย, ประเภทข้อมูลที่เกี่ยว (E/C/A/ทุกประเภท), การ์ดที่ใช้, บทบาทขั้นต่ำ, ข้อมูลขั้นต่ำ (ช่วงเวลา, จำนวนรายการ), สิ่งที่ต้องขอเพิ่มถ้าขาด
- อยู่ใน engine เป็นโครงสร้างข้อมูล (ใช้คำนวณ) และใน AIDA-18 เป็นคำอธิบาย (ให้ AIDA จับคู่ภาษาธรรมชาติ) — validator ตรวจว่าตรงกัน
- ครอบคลุม C1: R1–R4 เดิมของ B1 (E) + ความเสี่ยงของ C (ผู้ชำระหลายสัญญา, ตกแต่งสถานะค้างชำระ, ชำระซ้ำ/คืนเงินผิดปกติ, ปิดบัญชีก่อนกำหนดจากผู้ชำระอื่น) + A (จ่ายซ้ำ, แบ่งรายการหลบวงเงิน, SoD, ผู้ขายกระจุกตัว, ยอดผิดธรรมชาติ) + ความเสี่ยงทั่วไป (ยอดโดดเด่น, ช่วงสิ้นงวด, นอกเวลา)

### 4.5 โหมดสำรวจ
```
1. AIDA แจ้ง "ไม่มีการ์ดรับรองสำหรับคำถามนี้ — วิเคราะห์ในโหมดสำรวจ"
2. df = aida.data(intake)   ← ข้อมูลที่แปลงบทบาท/ตัวกรองแล้ว (รวม custom)
3. AIDA เขียนโค้ด pandas เอง (ห้ามแก้ engine, ห้ามใช้แทนการ์ดที่มีอยู่)
4. explore_id = aida.explore_log(question, code, result_df, note)
   → บันทึกคำถาม, โค้ดเต็ม, ผล, เวลา ลง Run Log + sheet "Exploratory"
5. แสดงผลพร้อมป้าย "โหมดสำรวจ — ยังไม่ผ่านการรับรอง" + ข้อจำกัด
6. ผู้ตรวจสอบสั่งเลื่อน → aida.promote(explore_id, entity, risk, period, reason, reviewer)
   → Finding: source="exploratory", Confidence ≤ "กลาง", reviewer บังคับ, ป้ายถาวร
```
- ถ้อยคำไม่กล่าวหา; ตัวเลขเกณฑ์ต้องอ้าง AIDA-14 หรือระบุว่า "ผู้ใช้กำหนด"
- `risk` ของ Finding สำรวจ: เลือกจาก Risk Library หรือ `RX` (ความเสี่ยงจากโหมดสำรวจ) + คำอธิบาย

### 4.6 Mapping profile (บันทึกการจับคู่ไว้ใช้ซ้ำ)
- `aida.save_mapping(intake, name)` → `mapping-<name>.json`: บทบาท, ความหมายคอลัมน์, ความหมายค่ารหัส (เช่น STS: A/R/C), ตัวกรอง, ค่าเกณฑ์องค์กร, ผู้ยืนยัน, วันที่
- รอบถัดไป: `inspect(files, brief, mapping=...)` ใช้ค่าเดิม และ **ถามเฉพาะสิ่งที่เปลี่ยน** (คอลัมน์ใหม่/หาย/รูปแบบเปลี่ยน)
- เก็บที่ SharePoint ของทีม (ผู้ใช้เลือกที่เก็บ)

### 4.7 AIDA-14 Registry v1.2
- คง key B1 ทั้งหมด
- เพิ่ม key การ์ดใหม่ (ค่ามาตรฐาน/แนวปฏิบัติทั่วไป ระบุที่มา): จ่ายซ้ำ (ช่วงวัน), ใกล้วงเงิน (ใช้ `FOR.THRESHOLD_AVOID.BAND` เดิม + จำนวนรายการ/ช่วงวันของการแบ่งรายการ), ชำระใกล้วันครบกำหนด (จำนวนวันก่อน due, สัดส่วนงวด), ผู้ชำระหลายสัญญา (จำนวนสัญญาขั้นต่ำ), Benford/ยอดกลม/ยอดซ้ำ (key FOR.* เดิม), ช่วงสิ้นงวด (`TEMP.PERIOD_END.WINDOW` เดิม), การกระจุกตัว (`CONC.*` เดิม), Intake (เกณฑ์ความมั่นใจของ suggest_roles)
- ค่าองค์กรจาก Intake ข้อ C ใช้แทนเฉพาะ run นั้น และบันทึกใน Run Log + Workbook

## 5. Engine API (`aida_engine.py`)
| ฟังก์ชัน | หน้าที่ |
|---|---|
| `inspect(files, brief=None, mapping=None, cfg=None) -> dict` | ทุกอย่างในข้อ 4.3 ข้อ 2 → `intake` (draft) + ข้อความสรุปสำหรับ AIDA |
| `confirm(intake, answers) -> dict` | ใส่คำตอบผู้ตรวจสอบ (บทบาท, ตัวกรอง, ค่าองค์กร, ความเสี่ยงที่เพิ่ม, Materiality) → `intake` ที่ยืนยัน + `intake.json` |
| `run(files, intake, out_dir) -> dict` | วิเคราะห์ตามแผน → รวมผล → C/M/P → Money Flow (E) → Workbook/CSV/Dashboard + Run Log |
| `data(intake) -> DataFrame/dict` | ข้อมูลที่แปลงบทบาท/ตัวกรองแล้ว สำหรับโหมดสำรวจ |
| `explore_log(question, code, result, note) -> str` | บันทึกโหมดสำรวจ |
| `promote(explore_id, entity, risk, period, reason, reviewer) -> dict` | เลื่อนเป็น Finding (Confidence ≤ กลาง) |
| `trace(acct, direction="both", period=None)` | Money Flow ตามคำสั่ง (E) |
| `save_mapping(intake, name)` / mapping ใน `inspect` | ข้อ 4.6 |
| `__version__`, `REGISTRY_VERSION` | ต้องตรงกับ AIDA-00/19 และ AIDA-14 |
- pandas ≥ 1.5, numpy, openpyxl, standard library เท่านั้น; ห้าม import ไลบรารีเครือข่าย
- ทุกฟังก์ชันคืนข้อความผิดพลาดภาษาไทยที่บอกวิธีแก้ (ไม่ใช่ traceback ดิบ)
- เกณฑ์ทั้งหมดจาก Machine Config ใน AIDA-14 (engine อ่านจากไฟล์ AIDA-14 ใน Knowledge หรือ dict ที่ส่งเข้ามา)

## 6. Output (เพิ่มจาก B1)
Workbook sheet ใหม่: **`Intake_Review`** (บริบท, Risk Concern, ความพอเพียง, ความเสี่ยงที่แนะนำ + คำตอบผู้ตรวจสอบ), **`Data_Dictionary`** (คอลัมน์, ความหมาย, บทบาท, ค่ารหัส, ผู้ยืนยัน, วันที่), **`Data_Request`**, **`Exploratory`** (คำถาม, โค้ด, ผล, ผู้เลื่อน) — นอกนั้นคงตาม B1 (README, Profile, Plan, Evidence, Findings, Mule_Networks, Money_Flow, Materiality, Run_Log)
Dashboard: เพิ่มแท็บ **Intake** และป้าย "จากโหมดสำรวจ" บน Finding ที่ promote; แท็บ Mule Networks / Money Flow แสดงเมื่อเป็นข้อมูล E

## 7. การทดสอบ

### 7.1 Spike ใน Copilot (งานแรก)
`spike-c1/`: `aida_engine_probe.py` (+ `.txt`), prompt 5 ข้อ + ตารางผล
1. Code Interpreter เห็นไฟล์ใน Knowledge ไหม
2. import engine จาก Knowledge ได้ไหม (.py / .txt)
3. ทางสำรอง: อ่าน engine จาก SharePoint/ไฟล์แนบแล้ว import ได้ไหม
4. ตัวแปร Code Interpreter อยู่ข้ามข้อความไหม
5. Knowledge รับไฟล์ .py ไหม
**กติกา**: ข้อ 2 ผ่าน → แนวทาง 3; ข้อ 2 ไม่ผ่านแต่ข้อ 3 ผ่าน → แนวทาง 2; ไม่ผ่านทั้งคู่ → หยุดและปรึกษาผู้ใช้

### 7.2 ข้อมูลตัวอย่าง (seed คงที่)
| ชุด | กรณีที่ฝัง |
|---|---|
| E | ชุด B1 เดิม — ต้องได้ 19 Finding + 1 เครือข่าย |
| C | ผู้ชำระคนเดียว 6 สัญญา, ชำระก่อนครบกำหนด 1–2 วันทุกงวด, ชำระซ้ำ, ยอดติดลบ (คืนเงิน), สถานะยกเลิก |
| A | จ่ายซ้ำ (invoice เดียวกัน), แบ่งรายการต่ำกว่าวงเงิน, ผู้บันทึก = ผู้อนุมัติ, Benford ผิดรูป, ยอดกลมกระจุก |
แต่ละชุด: คำอธิบายผู้ตรวจสอบตัวอย่าง (`brief.md`), เฉลย Finding, **เฉลย Intake** (สถานะความพอเพียง, Data Request, ความเสี่ยงที่ต้องถูกแนะนำ, คำอธิบายที่ต้องถูกจับว่าขัด), และ **ชื่อคอลัมน์ 3 แบบ**

### 7.3 Tests ใน repo
- การ์ดทุกใบ: พบกรณีที่ฝัง + ไม่มี false positive ในข้อมูลปกติ
- `profile_columns`, `suggest_roles` (3 แบบชื่อคอลัมน์; รหัสย่อไร้ความหมาย → "ไม่ทราบ"), `check_descriptions`, `assess_sufficiency`, `suggest_risks` (ตรงเฉลย, deterministic)
- `confirm` + `run` จาก `intake.json` ใหม่ (จำลองตัวแปรหาย) ได้ผลเท่าเดิม
- โหมดสำรวจ: `explore_log` ครบ, `promote` cap Confidence/บังคับ reviewer/ป้าย
- mapping profile: บันทึก/โหลด/แจ้งเมื่อคอลัมน์เปลี่ยน
- Regression B1: เฉลย E, วันที่ไทย, เพดาน 80,000 แถว, output เปิดได้ (openpyxl, Chromium), XSS/กันสูตร
- pandas 3 และ 1.5.3

### 7.4 Eval ใน Copilot (~15 ข้อ)
แยก brief ครบ; จับคำอธิบายที่ขัด; เดาแล้วถามก่อนรัน; ความพอเพียง + Data Request ตรงเฉลย; แนะนำความเสี่ยงแต่ไม่เพิ่มเอง; ยืนยันครั้งเดียวแล้ววิเคราะห์จนจบ; คำถามนอกการ์ด → โหมดสำรวจ + ป้าย → promote ตามกติกา; ข้อมูลประเภท C2/C3 → แจ้งขอบเขต + ใช้การ์ดกลาง/โหมดสำรวจ; mapping profile รอบสองถามเฉพาะส่วนที่เปลี่ยน

### 7.5 Validator เพิ่ม
- Knowledge = 20 ไฟล์
- engine: `__version__` ตรงกับ AIDA-00/19; `REGISTRY_VERSION` ตรงกับ AIDA-14; ไม่ import ไลบรารีเครือข่าย; ทุก `cfg["KEY"]` มีใน AIDA-14
- Risk Library: ทุกความเสี่ยงอ้างการ์ดที่มีใน engine และบทบาทใน 14 บทบาท; รายการใน engine ตรงกับ AIDA-18
- การตรวจเดิม (คำกล่าวหา, cross-ref, Instructions ≤ 8,000)
